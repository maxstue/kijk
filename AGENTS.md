# Kijk Agent Instructions

## Project Structure

**pnpm monorepo** with app and package workspaces:

- `apps/` — api (dotnet), client (React/TanStack Start)
- `packages/` — `@kijk/api` (typed API client, query keys, query/mutation options), `@kijk/ui` (shared components), `@kijk/core` (utilities, stores, hooks), `@kijk/config` (shared tsconfig/lint/format configs), `@kijk/openapi-codegen` (generates the API types)

## Developer Commands

### Root (pnpm)

```bash
pnpm dev          # client + api (parallel)
pnpm dev:client   # client only
pnpm dev:api      # api only
pnpm build        # all apps (parallel)
pnpm lint         # lint all workspaces
pnpm fmt          # check formatting in all workspaces
pnpm release      # auto-changelog + GitHub release (CalVer: yyyy.mm.minor)
```

### Client (`apps/client`)

```bash
pnpm dev          # Vite+ dev server via Infisical
pnpm build        # typecheck and Start/Nitro build
pnpm start        # production Node server (.output/server/index.mjs)
pnpm lint         # oxlint
pnpm fmt          # oxfmt --check
pnpm fmt:fix     # oxfmt
pnpm typecheck    # tsc --noEmit
```

### API (`apps/api`)

```bash
dotnet watch run --project src/Api/Api.csproj --launch-profile https
dotnet build src/Api/Api.csproj -c Release
dotnet format --verify-no-changes --exclude '**/Migrations/'
dotnet ef database update
```

## Package Structure

- **`@kijk/api`** — Typed client for the Kijk API: generated OpenAPI types, requests, query keys, `queryOptions` and `mutationOptions`; browser apps call `configureApiClient()` once at startup. Use `createApiClient()` for isolated transports; never share user authentication through a global server client.
- **`@kijk/ui`** — UI components (buttons, dialogs, etc.) using Base UI (`@base-ui/react`)
- **`@kijk/core`** — Zustand stores, hooks (use-mobile), browser-storage, logger
- **`@kijk/config`** — Shared lint/format config exports (oxlint/oxfmt)

## Architecture Notes

- **Client**: TanStack Router auto-generates `src/routeTree.gen.ts` — do not edit manually
- **Client rendering**: `apps/client` is the single TanStack Start web app. Public pages render on the server; `/_authenticated` uses `ssr: false`. Create the router and QueryClient per request. Browser initialization belongs in `src/client.tsx` or browser-guarded router setup.
- **Client integrations**: reusable integrations live in `shared/lib`; root-only authentication providers and theme bootstrap live in `app/root`. Initialize browser telemetry services directly in the browser-only router setup. Server code, including the `getSession` server function that the router injects as `context.auth`, lives in `server`. Features use the `shared/runtime` auth contracts. Clerk follows its TanStack Start setup: `clerkMiddleware` in `start.ts`, `ClerkProvider` in the root `shellComponent`, `auth()` only in server code, and every client import from `@clerk/tanstack-react-start`. Clerk SDK imports belong to `app/root/auth-provider.tsx` and the web login UI in `app/auth`; keep Start/server imports out of features and shared code.
- **Web BFF**: the browser calls same-origin `/api/*` only; the API is private, has no CORS and is reached solely through the server-only `API_URL`. Start validates the Clerk session per request, attaches the token on the server and relays only operations of the OpenAPI document (`@kijk/api/generated/operations`, regenerated by `pnpm api:generate`). `start.ts` applies same-origin CSRF checks to server functions and `/api/*`; the relay also requires the `X-CSRF: 1` header that the browser API client sends. Only allowlisted headers pass in either direction, bodies are streamed with a 16 MiB limit, and responses are `no-store`. .NET remains responsible for all domain authorization and per-user rate limits. `APP_URL` defines the canonical origin behind hosting proxies. See `apps/client/README.md` for deployment and authentication limits.
- **Client feature boundaries**: `routes/*` defines route context and page structure (search validation, loaders, pending/error states, layout shell, and feature composition); `app/<feature>/*` owns feature components, forms, sections, hooks, schemas, and feature logic; `app/<feature>/*` must not import another feature folder directly; `shared/*` must not import from `app/*`; enforced by `@kijk/oxlint-plugin-boundaries`
- **Project documentation**: maintain project documentation in the Kijk team documents in Linear. Update the existing relevant document instead of adding Markdown guides or a `docs/` directory to the repository. Keep concise setup/entrypoint information in READMEs and agent instructions in `AGENTS.md`; link to the canonical Linear documentation.
- **React composition**: compose existing `@kijk/ui` components directly; repeated UI JSX is acceptable. Extract by responsibility, not line count. Use `children`/slots for variable content, and compound components when callers compose a coherent family of optional or rearrangeable parts. Export flat names such as `PageToolbar`, `PageToolbarControls`, `PageToolbarActions` and `ImportReviewTransactions`; do not expose app-facing parts through an object namespace. Follow the local shadcn-style UI examples. Add local Context only for real shared state or behavior; layout compounds need no Context. Keep hooks in their owning components and avoid wrapper hooks returning large state/mutation objects. Reuse React Hook Form's provider for fields. Preserve state and mutation lifetimes across collapsed panels, menus and step changes. See [component composition](https://linear.app/justmax/document/architecture-62a60c95919b#react-component-composition) for decision rules and examples.
- **React props**: declare props with a named interface such as `ComponentProps` for every React component, including extracted/local components and test components or fixtures. Inline props types such as `function Component({ value }: { value: string })` are not allowed. Prefer interfaces over object-type aliases, and do not place object, intersection or utility types directly in component signatures. Interfaces may extend native or library props; preserve necessary discriminated unions through named interface variants.
- **Client feature file naming**: feature folders act as namespaces. Inside `app/<feature>`, omit the feature name from file names when the folder already provides that context. Prefer reserved feature-local names like `constants.ts`, `types.ts`, `schemas.ts`, `helpers.ts`, `utils.ts`, `columns.tsx`, and `options.ts`. Component files stay kebab-case, while exported React components stay PascalCase and should remain understandable outside their file.
- **Client data access**: reusable API calls, query keys, `queryOptions`, and `mutationOptions` live in `packages/api` (`@kijk/api`); keep feature form schemas inside their feature folders. Regenerate the API types with `pnpm api:generate` after API changes
- **Client query keys**: use `packages/api/src/query-keys.ts` for cache reads, writes, and invalidations instead of ad hoc key arrays
- **Client cache invalidation**: each `mutationOptions` invalidates or updates what its API change affects (via `onSuccess` and the mutation context's `client`); components only add UI reactions such as toasts, navigation or closing dialogs, preferably as `mutate(..., { onSuccess })` callbacks. A hook-level `onSuccess` replaces the one from the options, so call `options.onSuccess` from it
- **API**: Clean Architecture layers: Api → Application → Domain/Infrastructure/Shared
- **API use-case naming**: feature folders and namespaces provide the domain context. Use short local names such as `StatisticsHandler`, `RecordHandler`, `ConfirmMappingHandler` and `HandleAsync` for a single use case; name shared query methods after their operation (`ListAsync`, `DetailsAsync`, `OverviewAsync`). Keep existing query grouping where appropriate. Use `Handler.cs` inside a use-case folder. Public request/response DTO names retain enough context to be unique in OpenAPI.
- **API endpoint names**: endpoint methods use local operation names (`List`, `Details`, `Statistics`, `Record`, `ConfirmMapping`); every endpoint declares a globally unique `.WithName("Feature.Operation")`. Keep `CreatedAtRoute` and `AcceptedAtRoute` references aligned with these names.
- **API client naming**: request functions and query/mutation options in `packages/api/src/<feature>` omit the feature name (`getStatistics`, `statisticsQueryOptions`, `recordMutationOptions`). Use feature namespace imports at cross-feature call sites, e.g. `budgetsOptions.statisticsQueryOptions(...)`. Use `remove` and `exportCsv` for request functions where JavaScript reserves `delete` and `export`.
- **API registration**: every Application feature owns a `ModuleService : IModule` that explicitly registers its handlers and injectable helper services. Use `Scoped` for request/job services, especially those using `AppDbContext` or `CurrentUser`. Source generators in `Api.SourceGenerators` discover modules, endpoint groups (`IEndpointGroup`) and FluentValidation validators (one per request type).
- **API service ownership**: feature services belong to their feature module; central Application registration only composes modules, validators and shared services such as `TimeProvider`. Infrastructure owns technical adapters and their registrations. Pure static calculations do not need DI.
- **API documentation**: document public API request/response contracts and important domain rules; XML output stays enabled for OpenAPI. Do not add comments that only repeat handler, parameter, or adapter names. Missing-documentation errors are scoped to dedicated contract files in `apps/api/.editorconfig`.
- **API response mapping**: map entities to responses with Mapperly (`[Mapper]` static partial classes, one `ToResponse` for entities and one for `IQueryable` projections); `Application/MapperDefaults.cs` requires every response member to be mapped or explicitly ignored. Map by hand only when the mapping needs request context (e.g. `CurrentUser`) or filters inside a handler query
- **API authorization**: Clerk only authenticates. Roles and permissions are space-scoped, stored in the database, and defined as code catalogs in `Domain/Authorization` (`SpacePermissions`, `SpaceRoles`, seeded via EF `HasData`). Check permissions, never role names. Every authenticated endpoint must declare one of `.RequireSpacePermission(...)` (active space), `.RequireRouteSpacePermission(...)` (handler checks the route space via `AuthorizeSpaceAsync`), or `.WithoutSpacePermission(reason)`; `EndpointAuthorizationTests` enforces this. The client mirrors the catalog in `packages/api/src/spaces/permissions.ts`.
- **Private finances**: spaces group users, their roles and all data. Every user has a personal space (`Space.IsPersonal`) that is never deleted and never shared. In shared spaces, accounts and budgets can be private (`OwnerId`); transactions and imports inherit the visibility of their account. Read finance data only through `Application/Shared/Finances/FinanceQueryExtensions` (`GetSpaceAccounts`, `GetVisibleTransactions`, `GetVisibleBudgets`, `GetVisibleImports`), and guard changes to shared items with `AuthorizeSharedChangeAsync`.
- **Telemetry**: Sentry and PostHog receive the same data so they can be compared. Errors are scrubbed to type, stack frames and allowlisted identifiers (API: `TelemetryEventScrubber`, `PostHogEventScrubber`; client: `error-event-scrubber.ts`). Traces are OpenTelemetry spans exported over OTLP to both tools: the API registers them in `Infrastructure/Telemetry/TelemetryDependencyInjection.cs` (allowlist in `TraceScrubbingProcessor`), the client lazy-loads `shared/lib/tracing-provider.ts` only after performance consent. Keep both tools configured identically; a new span attribute or error property is added to the allowlists of both. Tools without configuration are skipped.
- **Feature flags**: PostHog flags `finances` and `ai-import` (keys in `AppConstants.Features`) are enforced by the API (`RequireFeature` on the finance endpoint groups, `AiGate` for the AI) and read by the client through `useFeature`, which loads the API's decision (`GET /api/users/me/features`) instead of asking PostHog, so both always agree. The API evaluates them locally (`PostHogFeatureFlags`): it downloads only the flag definitions, so no user data reaches PostHog; only global boolean switches with unconditional 0% or 100% release conditions are supported. Targeting, variants and partial rollouts stay off. The reader takes no user id. Configured fallbacks apply when no definitions are available; failed refreshes retain the last definitions.
- **Database**: PostgreSQL via Docker Compose; schema managed with `dotnet ef`
- **API package**: `@kijk/api` exports every module from `src/*` (e.g. `@kijk/api/transactions/options`)
- **UI package**: `@kijk/ui` exports from `src/components/*`
- **Core package**: `@kijk/core` exports from `src/lib/*`, `src/hooks/*`, `src/stores/*`

## Important Conventions

- **Node/pnpm**: Managed via `package.json` (`engines`, `devEngines`)
- **.NET**: 10.0 (per `global.json`)
- **Vite+ config**: `apps/client/vite.config.ts` configures the client app.
- **Format config**: `oxfmt.config.ts` (printWidth: 120, singleQuote, LF line endings)
- **Client lint/format**: Uses oxlint/oxfmt (NOT eslint/prettier for code style)
- **Frontend checks**: After client/frontend edits, always run React Doctor on the changed code. If it fails, committing is still allowed, but the final response must include a clear warning with the failed command and reason.
- **Client tests**: Colocate unit, component, and route tests with the source file they test. Reserve `apps/client/src/test` for E2E tests and shared test setup (including render helpers and mocks). The TanStack Router plugin ignores `.test.*` and `.spec.*` files through `routeFileIgnorePattern`.
- **Pre-commit hooks**: husky + lint-staged configured (runs on commit)

## React Patterns and Best Practices

- **Compiler first**: React Compiler is enabled for the client. Prefer plain calculations, objects and event handlers over `useMemo`, `useCallback` and `React.memo`. Do not add manual memoization by default. When removing existing memoization, test the affected interactions and the production build; a configured compiler does not prove that every component is compiled.
- **Compiler boundaries**: Keep incompatible mutable APIs, such as TanStack Table/Virtual integrations, isolated in small components. Keep pure filtering and data preparation in compilable parents. Preserve justified `use no memo` boundaries and explain their dependency constraint; do not silence compiler diagnostics or rely on memoization for correctness.
- **Modern patterns when useful**: Prefer composition and focused custom hooks. Use compound components and explicit slots for UI parts that belong together, with controlled state owned by their common parent. Use nullable contexts with checked consumer hooks instead of casted empty defaults. Keep accessible names, keyboard interaction, focus management and native semantics intact.
- **Async React**: Use the existing TanStack Router/Query integration for asynchronous data. Start independent requests in parallel in loaders or prefetch them before rendering. Place Suspense boundaries around the components that actually suspend, with local fallbacks that reserve layout space. Pair them with error boundaries and coordinated query/router retry. A normal `useQuery` needs its own loading, error/retry and successful-empty UI; Suspense does not handle it automatically.
- **Actions and responsiveness**: Use transitions, `useDeferredValue`, Actions/`useActionState`, or optimistic updates when they solve a concrete interaction problem. Prefer the existing Query mutation and form lifecycle over introducing a second source of server/form state. Deferred rendering is not network debouncing; optimistic updates need a defined rollback and reconciliation strategy.
- **Avoid unnecessary Effects**: Derive display data directly from props, URL state and query results. Handle user actions in event handlers or mutation callbacks. Reset state through explicit ownership, component keys or event updates rather than chains of Effects. For example, derive `const range = selectedRange ?? (isMobile ? '7d' : '90d')` instead of synchronizing another state variable in an Effect.
- **External synchronization only**: Effects are appropriate for DOM APIs, observers, subscriptions and external SDKs. Clean them up and depend on the primitive values that define the synchronization. Define helpers inside the Effect when possible; use `useEffectEvent` for subscription callbacks that need current state without recreating the subscription. Never omit real dependencies to force a lifecycle.
- **Browser subscriptions**: Prefer `useSyncExternalStore` with a stable snapshot and an explicit server snapshot for mutable browser state such as media queries. Keep initial SSR/hydration behavior intentional. Do not copy a changing external value into a one-time state initializer when it should remain a derived default.
- **Pure rendering and immutable data**: Do not mutate props, state or Query cache results, including nested arrays. Use immutable derivation or the Query client's update API. Never send telemetry, write storage or show toasts during render. Read time-dependent form defaults once with a lazy initializer; keep reusable Intl formatters outside render when their configuration is fixed.
- **Mutation coordination**: Scope conflicting mutations to the affected resource, expose shared pending state through mutation keys, and keep destructive/finalizing actions disabled until writes and their awaited cache invalidations settle. A row-local `isPending` does not protect a parent Save, Reset or AI action.
- **External notifications**: Synchronize toasts and SDKs by meaningful state changes, not newly allocated object/array identities. Deduplicate unchanged notifications, dismiss removed warnings and scope their identifiers to the relevant space/period. Report caught errors in boundary/router callbacks, and keep fallback components presentational.
- **Maintainability and validation**: Split files by responsibility (for example, list orchestration, row actions, bulk actions and wizard steps), not by an arbitrary line limit. Keep user-visible filters/views in route search state when navigation persistence matters. Add regression tests for changed behavior, run the affected workspace checks and React Doctor, and distinguish static review from browser, production-build and remote-CI evidence.

Use the current official React guidance when evaluating these choices:
[React Compiler](https://react.dev/learn/react-compiler/introduction),
[You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect),
[Removing Effect Dependencies](https://react.dev/learn/removing-effect-dependencies),
[Separating Events from Effects](https://react.dev/learn/separating-events-from-effects),
[useSyncExternalStore](https://react.dev/reference/react/useSyncExternalStore), and
[Suspense](https://react.dev/reference/react/Suspense).

## CI (GitHub Actions)

- **Deployments**: production deployments run exclusively through the existing CI/CD workflow. Do not run `railway up` or manually redeploy services. Prepare required Railway UI settings for review; do not introduce deprecated Railway JSON/TOML config files.
- **Entry workflows** (`ci.yml`, `deployment.yml`) only define triggers and compose building blocks; they contain no check logic.
- **Reusable workflows** (`.github/workflows/_*.yml`) are the building blocks, one per area: `_changes` (path filter, PRs only), `_js-workspace` (one JavaScript app or package), `_dotnet` (one .NET app), `_js-e2e` (E2E tests for one app), `_js-audit`, `_sonar` (reuses the coverage artifacts of the same run). `ci.yml` calls `_js-workspace` and `_dotnet` once per app or package, so each has one job in the checks list and graph. Its steps run sequentially: format, lint, build (or typecheck), tests and, for .NET, audit. Workspace jobs run independently in parallel.
- **Composite actions** (`.github/actions/*`) hold shared steps: `setup-js` (Vite+, install, cached Playwright), `setup-dotnet`, `deploy-railway`, `migrate-database`, `create-release`.
- `ci-result` is the only required status check.
- New app or package: add an `apps-<name>` or `packages-<name>` job in `ci.yml` that calls `_js-workspace.yml` (inputs `workspace`, `directory`, optionally `build`, `test`, `browser`, `browser-directory`) or `_dotnet.yml` (inputs `workspace`, `directory`, `solution`, optionally `format-exclude`), and add it to the `needs` lists of `sonar` and `ci-result`; Sonar picks up its coverage automatically. A JavaScript workspace needs the scripts `fmt`, `lint`, `typecheck` (plus `build` / `test:coverage` if enabled). For E2E, add a separate caller of `_js-e2e.yml` (inputs `workspace`, `directory`, optionally `command`, `timeout`, `secrets-env`, `secrets-path`) that needs the app checks, grants `id-token: write` for Infisical, and is included in `ci-result.needs`. Workspace checks need only read access. Browser setup uses the workspace directory; `browser-directory` can select another workspace that provides the Playwright CLI. E2E uses its app directory for browser setup and test execution.
- The checks within a workspace run sequentially with one setup; E2E waits for that app's checks. Sonar waits for workspace coverage and can run alongside E2E; `ci-result` also requires E2E to pass. On pull requests, `_changes` selects the affected JavaScript workspaces (changed ones plus their dependents, via pnpm) and the other blocks are skipped; changes to shared files (root manifests, lockfile, JavaScript CI) check all of them.
